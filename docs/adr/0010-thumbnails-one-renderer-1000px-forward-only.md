# ADR 0010 — Thumbnails: one renderer, 1000 px, forward-only

- **Status:** Accepted, 2026-08-21
- **Deciders:** S. Le Boulanger
- **Related:** ADR 0002 (gate D3), ADR 0009 (materials committed), ADR 0003 (URLs are frozen)

## Context

Three thumbnail widths coexist in the org today, produced by two renderers, and no gate anywhere notices. Measured on disk:

| Set | n | Width | Avg size | Produced by |
|---|---|---|---|---|
| `fle` + `daf` presentations | 216 | 900 px | 20 / 17 KB | `build_materials_latex.thumb()` at `:311-315`, `z = 900 / pg.rect.width` |
| `fle` + `daf` worksheets | 216 | 900 px | 99 / 105 KB | same |
| `daf/static/downloads` exams | 60 | 1280 px | 179 KB | `render_thumbs.py:37`, `TARGET_WIDTH = 1280` |
| `efl`, everything | 0 | — | — | git-ignored (ADR 0009) |

That is **492 committed PNGs** across two independent implementations of the same operation.

The second renderer also has a coverage hole. `render_thumbs.py` loops `WORK` at `:103` and `EXAMS` at `:113`, but globs `PRES` only for `*.pptx` and `*.odp` at `:128` and `:138`. Since the LaTeX migration there are no `.pptx` or `.odp` sources, so deck thumbnails have been produced solely as a side-effect of `build_materials_latex.py:365`. It carries a LibreOffice branch (`:40-51`, `:66-87`, `:91-97`, `:123-138`) matched by a `libreoffice-impress` install at `daf/.github/workflows/hugo.yml:50-53`, which under ADR 0009 has no reason to exist.

The consumer sets the requirement. `.material-card img` renders at up to 320 CSS px in a `repeat(auto-fit, minmax(220px, 1fr))` grid (`custom.css:500-506`, card at `:508-515`). At 2× device pixel ratio that needs 640 device px.

## Decision

**One renderer, one width, one compressor, applied forward-only.**

- **Renderer:** `render_thumbs.render_pdf` is the only implementation. `build_materials_latex.thumb()` is deleted and delegates to it. The missing `PRES.glob("*.pdf")` loop is added. The LibreOffice branch is deleted along with the apt install at `daf/.github/workflows/hugo.yml:50-53`.
- **Output:** PNG, page 1, `alpha=False`, PyMuPDF, target width **1000 px**, then `oxipng -o4 --strip safe`.
- **Scope: forward-only.** Everything generated from this decision onward is 1000 px. **The 492 existing thumbnails are not re-rendered.** Each one ages out at 1000 px the next time its source PDF changes.
- **`static/materials/thumbs.lock`** maps `pdf-sha256 → png-sha256 → png-width` for every PDF/PNG pair, plus a `standard:` field carrying `1000` or `legacy`. It is generated by `bin/kit materials --thumbs`, which is its only writer.

1000 px rather than 1280 because PNG size tracks area and 1280 buys nothing at 320 CSS px: `daf`'s 1280 px exam thumbnails average 179 KB against 105 KB for the same documents' 900 px worksheet thumbnails — 1.7× the bytes for no perceptible gain. 1000 px clears the 640 device px requirement with margin.

**Gate D3 is written against the deferral rather than around it.** D3 asserts:

1. Every PDF under `static/materials/` and `static/downloads/` has a sibling PNG.
2. `thumbs.lock` digest-matches every pair, so a regenerated PDF whose thumbnail was not refreshed fails.
3. `png-width == 1000 ± 2` for every row carrying `standard: 1000`, and for **any** pair whose `pdf-sha256` changed in this PR.

**D3 does not assert a width across the corpus.** Pre-existing thumbnails are recorded at their actual width with `standard: legacy`. New and regenerated thumbnails are held to the standard; existing ones are recorded, not rewritten.

## Consequences

- Two implementations of one operation collapse to one. The deck-thumbnail hole closes: decks stop depending on a side-effect of the LaTeX generator.
- LibreOffice leaves the org — the code branch and the CI install go in the same commit, which ADR 0009 requires independently.
- Widths stay mixed for a while, deliberately. `thumbs.lock` makes that state legible rather than accidental: every row says which standard it is at.
- The mixed state ends without a migration commit. `fle` and `daf` regenerate their PDFs during ADR 0012's front-matter migration and §9.3's exam completion anyway, and `daf`'s 60 exam PDFs come to 1000 px when P3.2 regenerates them through `kit/latex/` (ADR 0008). `efl`'s 360 thumbnails are all born at 1000 px in P3.4b, because it has none today.
- No thumbnail filename changes, so no URL changes and no VG Wort mark is touched. This decision is unaffected by the T.O.M. blockage.
- A thumbnail can drift visually from its PDF only if the PDF changed and the PNG did not, which is exactly what D3's digest match catches.

## Alternatives considered

**Bulk re-render of all 492 committed PNGs at 1000 px, in one commit.** Rejected. It writes roughly 15 MB of new blobs into git history to fix an inconsistency no learner perceives at 320 CSS px, and it produces a 492-file diff that no reviewer can meaningfully read. The deferral is recorded in §6's deferral register with "when each PDF next changes" as its trigger, not "never".

**Standardise on 1280 px.** Rejected on measured bytes: 179 KB against 105 KB for the same documents, 1.7× the payload, invisible at the size the card actually renders.

**Standardise on 900 px, the majority width, and re-render only the 60 exam thumbnails.** Rejected. 900 px is under the 2× DPR requirement of 640 device px only by a small margin, and it was never chosen — it is a hard-coded `z = 900 / pg.rect.width` in a helper. Picking the accidental value because more files carry it is not a standard.

**Keep both renderers and add a width assertion to reconcile them.** Rejected. Two implementations that a gate keeps in agreement is more machinery than one implementation, and it leaves the deck-glob hole and the LibreOffice dependency in place.
